# INHA AI Data Analysis LAB

AI·공공데이터 기반 경진대회 운영 시스템의 기본 코드 골격입니다.

## 실행

Node.js 22.12 이상(권장 24)에서 `npm ci` 후 `npm run dev`를 실행합니다.
기본 주소는 개발 서버에 표시되는 `/AI_data_analysis_lab/` 경로입니다.
`npm run lint`, `npm test`, `npm run typecheck`, `npm run build`로 검증합니다.

Supabase 연결 준비 시 `.env.example`을 `.env.local`로 복사하고 설정된 `AI_Career_Lab` 프로젝트 URL을 확인하고 해당 프로젝트의 공개 anon key를 입력합니다. 환경변수 없이도 공개 화면은 실행됩니다. 서버 관리자 키는 넣지 않습니다.

## 구조

- `src/app/`: 앱 라우팅
- `src/components/`: 공통 레이아웃과 UI
- `src/features/`: 인증·기수·팀·보고서 등 기능별 구현 위치
- `src/pages/`: 공개 홈과 오류 화면
- `src/lib/`: Supabase 클라이언트와 공통 유틸리티
- `src/types/`: 도메인 타입
- `src/styles/`: Tailwind와 전역 스타일
- `supabase/migrations/`: DB 및 RLS 변경 SQL과 적용 기록
- `supabase/functions/`: 계정 생성·연결, 최초 비밀번호 변경 서버 함수
- `.github/workflows/ci.yml`: lint와 빌드 검증

- 화면: `http://127.0.0.1:5173/AI_data_analysis_lab/#/participants`

- 교수만 참가자를 직접 등록·조회·수정·비활성화할 수 있습니다. 기수 선택, 검색, 상태 필터, 이름·학번·학과·이메일 정렬을 지원합니다.

- 참가 정보를 저장한 뒤 '대기 계정 일괄 처리'로 인증 계정을 생성·연결합니다. 연결 전에는 '계정 연결 대기'로 표시합니다.

- 신규 계정 생성·기존 계정 연결, 엑셀 일괄 업로드와 학생 본인 참가 정보 조회를 지원합니다. 계정 연결 후 팀 관리 화면에서 팀을 배정합니다.
- 입력 검증은 `tests/participants.test.mjs`, DB 검증은 `supabase/tests/ad_participants_access.sql`에 있습니다. DB 테스트는 임시 데이터를 모두 롤백합니다.

검증: 입력 검증 테스트 총 7개, lint·타입 검사·빌드 통과. 참가자의 생성·조회·수정·비활성화, 기수별 중복 제약, 역할별 접근 차단, 기수·연결 계정·수정 시각 변경 차단을 DB에서 확인했습니다. 실제 브라우저에서의 등록·수정 흐름은 사용자 검수가 필요합니다.

## 엑셀 등록과 계정 발급 (2026-09-24)

1. 참가자 관리에서 기수를 선택하고 엑셀 양식을 내려받습니다.
2. 이름·이메일·학과·학번·학년·전화번호·희망직무를 입력합니다. 학번과 전화번호는 텍스트 형식을 유지합니다.
3. 파일을 선택하고 오류·중복·등록 예정 행을 확인한 뒤 정상 행을 등록합니다.
4. '대기 계정 일괄 처리'를 실행합니다. 새 이메일은 계정을 생성하고 기존 이메일은 기존 계정을 연결합니다.
5. 새 계정의 임시 비밀번호를 이번 결과 화면에서 확인해 당사자에게 안전하게 전달합니다.
6. 학생은 최초 비밀번호 변경 후 자신의 활성 기수와 참가 정보를 조회합니다.

- `.xlsx` 2MB·500행까지 지원합니다. 수식·날짜·링크 셀, 기수명 불일치와 파일 내 중복은 차단합니다. 기존 참가자와 같은 행은 건너뛰고 다른 내용은 자동으로 덮어쓰지 않습니다.
- 계정 발급은 파일 등록과 별도 작업입니다. 임시 비밀번호는 암호학적 난수로 생성하며 전화번호·학번을 사용하지 않습니다. 평문은 발급 응답과 화면 메모리에만 존재하고 자동 이메일 발송·파일 다운로드는 하지 않습니다.
- 발급 응답을 잃어버리면 임시 비밀번호 원문은 다시 조회할 수 없습니다. 자동 재발급은 제공하지 않으며 관리자가 Supabase의 계정 복구 절차를 별도로 진행해야 합니다.
- 기존 Auth 계정의 비밀번호, 앱 역할, 비활성 상태는 임의로 덮어쓰지 않습니다. 연결된 참가자의 이메일 변경도 차단합니다.
- 공유 DB의 기존 Auth 트리거는 새 계정에 대해 기존 서비스 프로필도 자동 생성합니다. 해당 트리거는 수정하지 않았습니다. 학생이 비밀번호를 변경하면 동일 계정을 사용하는 다른 프로그램에서도 새 비밀번호를 사용합니다.

배포 함수: `ad-provision-account`, `ad-change-password`. 서버용 키는 Edge Function 런타임에서만 사용합니다.

검증: `npm test` 18개, `npm run check:functions`, 프론트엔드 빌드, DB 계정 연결·비밀번호 제한·학생 접근 테스트 통과. `npm run check:function-auth`로 배포 함수의 무인증·잘못된 토큰·공개 키 요청 차단을 확인했습니다. DB 테스트는 Auth 사용자와 기존 트리거가 만든 자료도 모두 롤백했습니다. 실제 참가자 계정 발급·비밀번호 변경 및 브라우저 전체 흐름은 아직 실행하지 않았습니다.

참고: [Supabase 계정 생성](https://supabase.com/docs/reference/javascript/auth-admin-createuser), [Edge Function 인증](https://supabase.com/docs/guides/functions/auth), [ExcelJS](https://github.com/exceljs/exceljs).

## 프로그램 일정 (2026-09-24)

- 화면: `http://127.0.0.1:5173/AI_data_analysis_lab/#/schedules`
- 교수는 프로그램을 선택하고 제목·설명·단계·시작/종료 일시·공개 범위를 등록·수정합니다. 제출 마감은 하나의 마감 일시로 설정합니다.
- 기획·설계·구현·발표·산출물 확인·기타 단계와 진행 중·예정/전체 필터를 제공합니다. 시간 입력·표시는 브라우저 위치와 무관하게 한국 시간(KST) 기준입니다.
- 새 일정은 기본적으로 참여 학생과 교수에게만 공개합니다. 전체 공개를 선택하면 프로그램명과 일정 내용이 로그인 전 홈에 표시됩니다.
- 학생은 활성 참가 정보가 연결된 본인 프로그램의 일정만 조회합니다. 학생 쓰기, 비활성 참가·프로필, 최초 비밀번호 변경 전 접근은 DB에서 차단합니다.
- 일정 취소·복원을 지원하며 기록은 유지합니다. 종료·취소 일정은 ‘전체’ 필터에서 확인합니다. 편집 중 이동과 새로고침에는 미저장 안내를 표시하고, 동시 수정 충돌은 덮어쓰지 않습니다.
- `AD_schedules`와 공개용 `AD_public_schedules()`를 기존 DB에 적용했습니다. 공개 RPC는 공개 지정 일정과 프로그램명만 반환하고 작성자·참가자 정보는 반환하지 않습니다.

검증: 테스트 23개, lint·타입 검사·빌드 통과. `supabase/tests/ad_schedules_access.sql`로 교수 관리, 학생 소속 제한, 비공개 보호, 날짜·마감 제약, 수정 충돌과 취소·공개 해제를 검증했으며 임시 자료와 권한 변경은 모두 롤백했습니다. 브라우저 조작 검수는 컴퓨터 제어 권한이 없어 실행하지 못했습니다.

- 한 참가자는 프로그램당 하나의 팀에만 소속됩니다. 팀을 이동하려면 기존 팀에서 해제·저장한 뒤 새 팀에 배정합니다. 팀장은 선택한 팀원 중 지정하며 미지정 상태도 저장할 수 있습니다.
- 기본 권장 인원 4~5명은 안내이며 저장을 차단하지 않습니다. 인원 기준의 강제 정책은 아직 확정하지 않았습니다.
- 학생: 소속 팀의 팀원·직무를 조회하고 프로젝트 주제·단계·Notion/GitHub/데모 링크를 수정합니다. 팀명·구성원·팀장 변경은 교수 전용입니다. 동시 수정은 버전 검사로 덮어쓰기를 차단합니다.
- 학생에게 팀원 이름·학과·희망 직무·팀장/활성 상태만 보여줍니다. 이메일·전화번호·학번은 팀원 조회 응답에 포함하지 않습니다. 소속 해제, 참가·프로필 비활성화, 최초 비밀번호 변경 전에는 소속 팀 접근을 차단합니다.
- 팀원·기획서·보고서가 남은 팀은 삭제할 수 없습니다. 향후 산출물 테이블도 `ON DELETE RESTRICT`로 팀 자료 보존을 유지해야 합니다.

검증: 테스트 27개, lint·타입 검사·빌드 통과. `supabase/tests/ad_teams_access.sql`로 원자적 저장, 중복·타 프로그램·미연결 배정, 팀장 제약, 학생 권한·개인정보 제한, 소속 해제와 동시 수정 충돌을 확인했습니다. 검증용 Auth 계정과 공유 트리거의 생성 자료까지 모두 롤백했습니다. 실제 운영 참가자 배정과 브라우저 조작 검수는 실행하지 않았습니다.

## 프로젝트 기획서 (2026-09-25)

1. 학생은 ‘내 팀’ 카드의 ‘기획서 작성·조회’를 선택합니다. 주소는 `#/teams/{팀 ID}/proposal`입니다.
2. 프로젝트명과 명세서의 6개 본문 항목을 작성합니다. 각 항목은 8,000자, 선택 Notion 링크는 2,000자까지 지원합니다. 외부 문서 동기화는 하지 않습니다.
3. 미완성 내용은 임시 저장할 수 있습니다. 제출하려면 6개 항목을 모두 작성해야 합니다. 같은 팀의 모든 활성 학생이 공동 작성하며 변경 충돌 시 입력 내용을 유지하고 다시 조회하도록 안내합니다.
4. 교수는 ‘팀 관리 → 기획서 조회·검토’에서 초안·제출 내용을 확인하고 제출된 기획서에 검토 완료 또는 수정 요청을 남깁니다. 수정 요청에는 사유가 필요합니다.
5. 제출·검토 완료 상태에서는 학생 수정을 잠급니다. 교수의 수정 요청으로 작성 중 상태로 돌아오면 팀원이 수정·재제출합니다. 교수는 학생 본문을 직접 덮어쓸 수 없습니다.

최종 변경자·시각, 최근 제출자·시각, 최근 검토자·시각·피드백을 기록하며 시각은 KST로 표시합니다. 최신 검토 피드백을 제공하며 별도 코멘트 목록·전체 변경 이력은 후속 구현 대상입니다. 미저장 이동·새로고침을 확인하고 기획서가 있는 팀은 삭제를 차단합니다.

검증: 테스트 31개, lint·타입 검사·빌드 통과. `supabase/tests/ad_proposals_access.sql`에서 공동 작성, 불완전 제출·상태 위조 차단, 제출·검토·수정 요청·재제출, 버전 충돌, 소속·계정 상태별 접근과 자료 보존을 확인했습니다. 검증 자료와 임시 Auth 사용자·공유 트리거 생성 자료는 모두 롤백했습니다. 브라우저 직접 조작 검수는 미실행입니다.

## 주간·일일 보고서 (2026-09-25)

- ‘내 팀’ 카드의 ‘보고서 작성·조회’에서 `#/teams/{팀 ID}/reports`로 이동합니다. 교수는 같은 화면에서 팀별 보고서 목록과 전체 내용을 조회합니다.
- 팀원은 일일·주간 보고를 각각 회차별로 작성합니다. 초안은 미완성 상태로 저장할 수 있고, 제출할 때는 진행 요약·완료 항목·다음 계획을 입력해야 합니다. 구분·상태 필터를 제공합니다.
- 제출 후 검토 전에는 ‘수정 저장’으로 제출 상태·제출자·제출 시각을 유지하며 내용을 바꿀 수 있습니다. ‘수정 후 제출’은 최근 제출자와 시각을 갱신합니다. 검토 완료 후에는 교수가 사유와 함께 수정 요청해야 다시 작성할 수 있습니다.
- 권한과 버전 충돌은 DB 함수에서 확인합니다. 변경자·제출자·검토자 및 각 시각을 보관하고, 보고서가 있는 팀의 삭제를 차단합니다. 피드백은 최신 검토 내용만 표시하며 독립 코멘트 목록과 제출 집계 대시보드는 후속 구현 대상입니다.

검증: 단위 테스트 35개, lint·타입 검사·빌드와 DB 롤백 권한 검증 통과. 임시 Auth 사용자와 공유 트리거 생성 자료는 모두 롤백했습니다. 브라우저 직접 조작 검수는 미실행입니다.

## 기획서·보고서 코멘트 (2026-09-25)

교수는 각 기획서·보고서 화면에서 코멘트를 등록하고 본인 코멘트를 수정·삭제할 수 있습니다. 현재 소속 팀원은 코멘트를 읽을 수 있습니다. 코멘트에는 작성자와 작성·수정 시각이 기록되며 검토 완료·수정 요청 상태와 별도로 관리합니다. 컨설턴트·연구원 권한과 타인 코멘트 관리 정책은 후속 구현 대상입니다.

## 프로그램 진행 현황 (2026-09-25)

교수 대시보드에서 프로그램을 선택하면 활성 참가자·팀 수, 기획서 제출률, 팀별 프로젝트 단계·기획서 상태·일일/주간 보고서 제출 건수·작성 중 건수·이슈/지원 요청 건수를 확인할 수 있습니다. 팀의 기획서·보고서로 바로 이동할 수 있습니다. 일일·주간 회차별 제출 팀 수와 미제출 팀도 구분해 표시합니다. 제출 예정 회차를 지정하는 설정은 아직 없으므로, 해당 회차의 보고서가 처음 생성된 뒤부터 미제출 팀을 계산합니다. 작성 중인 초안은 제출 건수에 포함하지 않습니다.

`AD_program_monitoring()`은 교수 권한을 DB에서 확인하며 한 요청에서 진행 현황을 집계합니다. 롤백 검증으로 수치·미제출 팀·학생/익명 접근 차단을 확인했습니다. 발표 준비율·산출물 제출률과 팀 전체리포트는 후속 구현 대상입니다.
